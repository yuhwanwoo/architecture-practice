System design · URL shortener

URL 단축기 확장 로드맵

스프링 부트 한 대와 해시맵에서 시작해 멀티 리전까지, 기술을 하나씩 들이는 순서다. 각 단계는 바로 앞 단계의 병목 하나를 푼다. 기준 규모는 생성 100 TPS, 리다이렉트 10,000 TPS, 10년 누적 300억 건.

이미 있던 것이 단계에서 새로 들어오는 것
  1. 0인메모리 Map스프링 부트 한 대, 메모리에 저장
  2. 1PostgreSQL + JPA관계형 DB 로 영속화
  3. 2DB 시퀀스 + Base62충돌 없는 키 생성
  4. 3로드밸런서 + 앱 수평 확장앱을 여러 대로
  5. 4Redis 캐시읽기를 DB 에서 떼어 낸다
  6. 5PostgreSQL 읽기 복제본캐시 미스 조회를 분산
  7. 6블룸 필터 + 네거티브 캐시없는 키 공격 방어
  8. 7Snowflake ID 생성기DB 시퀀스 의존 제거
  9. 8DB 샤딩저장소를 수평 분할
  10. 9읽기/쓰기 서비스 분리배포·스케일 단위 분리
  11. 10Kafka + ClickHouse클릭 분석을 비동기로
  12. 11GeoDNS + CDN + 멀티 리전지리적 확장
  13. 12API Gateway + Safe Browsing남용 방어

Stage 0 · 단일 서버

Step 0

스프링 부트 한 대, 메모리에 저장

도입 · 인메모리 Map

넘어가는 신호시작점. 도메인 로직(키 생성·리다이렉트·만료)만 먼저 굳힌다.

얻는 것

  • 생성·리다이렉트 API 와 테스트가 하루 안에 나온다.
  • 이 단계에서 이미 IdGenerator, ShortUrlRepository, ShortUrlCache 포트를 둔다. 이후 모든 단계는 이 세 포트의 구현체만 바꾼다.

대가

  • 프로세스를 재시작하면 전부 사라진다.
  • 인스턴스를 두 대 띄우면 서로의 키를 모른다.

코드에서 바뀌는 것InMemoryShortUrlRepository, RandomKeyGenerator (충돌 시 재시도)

Step 1

관계형 DB 로 영속화

도입 · PostgreSQL + JPA

넘어가는 신호첫 실배포. 재시작해도 링크가 살아 있어야 한다.

얻는 것

  • 영속성. 백업과 복구가 가능해진다.
  • short_key UNIQUE 제약이 충돌을 DB 레벨에서 막아 준다.
  • 단일 PostgreSQL 로 읽기 수천 TPS, 쓰기 수백 TPS 까지는 인덱스 조회만으로 버틴다.

대가

  • 모든 리다이렉트가 DB 왕복 1회 (약 1ms).
  • 앱도 DB 도 한 대. 둘 중 하나가 죽으면 서비스 중단.

코드에서 바뀌는 것JpaShortUrlRepository 로 교체. 테이블은 short_url(id, short_key, long_url, expires_at, created_at)

Step 2

충돌 없는 키 생성

도입 · DB 시퀀스 + Base62

넘어가는 신호랜덤 키의 충돌 체크 조회가 거슬리기 시작할 때. 사실상 Step 1 직후.

얻는 것

  • 시퀀스는 유일하므로 충돌 체크 조회가 사라진다.
  • 비트 셔플은 전단사 함수라 유일성을 유지한 채 순서만 섞는다. abc123 다음이 abc124 가 아니게 된다.
  • 7자 Base62 는 627 ≈ 3.5조. 하루 1천만 건 생성해도 900년.

대가

  • 생성마다 시퀀스 왕복 1회. 시퀀스를 INCREMENT BY 100 으로 배치 할당하면 줄어든다.
  • 해시 방식과 달리 같은 URL 을 두 번 넣으면 키가 두 개 나온다. 중복 제거가 필요하면 long_url 해시 인덱스를 따로.

코드에서 바뀌는 것DbSequenceIdGenerator, Base62, FeistelShuffle

Stage 1 · 읽기 확장

Step 3

앱을 여러 대로

도입 · 로드밸런서 + 앱 수평 확장

넘어가는 신호앱 CPU 70% 이상 유지, 또는 배포할 때마다 생기는 다운타임.

얻는 것

  • 앱 단일 장애점 제거. 롤링 배포가 가능해진다.
  • 앱에 세션이 없고 ID 는 DB 시퀀스가 발급하므로 몇 대를 띄워도 키가 겹치지 않는다.

대가

  • 이제 상태를 가진 건 DB 뿐이다. 병목이 DB 로 옮겨 간다.
  • DB 커넥션 수가 앱 대수에 비례해 늘어난다. 커넥션 풀 상한을 잡아야 한다.

코드에서 바뀌는 것코드 변경 없음. 인프라만 바뀐다.

Step 4

읽기를 DB 에서 떼어 낸다

도입 · Redis 캐시

넘어가는 신호DB 읽기 CPU 나 커넥션 포화, 리다이렉트 p99 상승. 읽기가 쓰기의 100배이므로 가장 효과가 큰 조치다.

얻는 것

  • 히트율 80~95% 면 DB 읽기가 1/5 ~ 1/20 로 준다. 캐시 히트 지연은 1ms 미만.
  • URL 은 생성 후 바뀌지 않으므로 캐시 불일치 문제가 거의 없다. 만료·삭제 시에만 DEL.

대가

  • Redis 가 죽으면 트래픽이 DB 로 전량 유입된다. DB 가 캐시 없이도 버틸 용량이거나 Step 5 가 먼저 와야 한다.
  • 메모리 비용. 핫셋 20% 기준 하루치면 수십 GB.

코드에서 바뀌는 것RedisShortUrlCache 가 NoopShortUrlCache 를 교체. ResolveShortUrl 은 그대로.

Step 5

캐시 미스 조회를 분산

도입 · PostgreSQL 읽기 복제본

넘어가는 신호캐시 미스분과 생성 트래픽만으로도 Primary 가 버겁거나, Redis 장애 시 DB 가 버틸 수 없을 때.

얻는 것

  • 읽기 용량이 Replica 수만큼 늘어난다.
  • Primary 장애 시 Replica 를 승격해 복구 시간을 줄인다.

대가

  • 복제 지연 수십 ms. 생성 직후 조회는 Step 4 의 write-through 가 가려 준다. 그래도 Replica 에 없으면 Primary 를 한 번 더 조회한다.
  • 쓰기는 여전히 Primary 한 대.

코드에서 바뀌는 것라우팅 DataSource. @Transactional(readOnly = true) 면 Replica 로.

Step 6

없는 키 공격 방어

도입 · 블룸 필터 + 네거티브 캐시

넘어가는 신호404 비율 급증과 함께 캐시 히트율이 급락할 때. 없는 키는 캐시에 없으므로 전부 DB 로 가고, 랜덤 키를 쏘면 캐시가 무력화된다.

얻는 것

  • 블룸 필터의 '없음' 판정은 100% 정확하다. 메모리 조회라 DB 도 Redis 도 건드리지 않는다.
  • 네거티브 캐시는 같은 없는 키를 반복해서 두드리는 패턴을 막는다.

대가

  • 블룸 필터는 '있음' 에 오탐이 있다 (1% 설정 시). 오탐분은 뒤 단계로 흘러가므로 문제는 아니다.
  • 키 300억 개·오탐 1% 면 필터가 약 36GB. 전역 하나는 비현실적이므로 Step 8 이후 샤드별로 두거나, 그 전까지는 네거티브 캐시 + Step 12 의 rate limit 조합이 현실적이다.

코드에서 바뀌는 것ShortUrlCache.putNegative(), KeyExistenceFilter 포트

Stage 2 · 쓰기·저장 확장

Step 7

DB 시퀀스 의존 제거

도입 · Snowflake ID 생성기

넘어가는 신호생성 TPS 가 올라 시퀀스 왕복이 쓰기 지연의 주요 부분이 되었거나, Step 8 샤딩 준비 (샤드마다 시퀀스면 유일성이 깨진다).

얻는 것

  • ID 생성이 네트워크 없이 끝난다. 쓰기 경로가 DB 왕복 1회로 준다.
  • 시간순 정렬이 되어 인덱스 삽입이 순차적이다.
  • 노드 ID 배정은 ZooKeeper/etcd 또는 K8s StatefulSet ordinal 로.

대가

  • 표준 64bit 는 Base62 로 11자다. 7자를 유지하려면 비트를 줄인 변형 (예: 초 단위 30bit + 노드 6bit + 시퀀스 6bit = 42bit) 을 쓰거나, 사전 발급 키 풀 (KGS) 로 간다.
  • 시계 역행 시 중복 위험. 역행 감지 시 대기하거나 예외.

코드에서 바뀌는 것SnowflakeIdGenerator 가 DbSequenceIdGenerator 를 교체.

Step 8

저장소를 수평 분할

도입 · DB 샤딩

넘어가는 신호단일 PostgreSQL 이 수 TB 를 넘고, 쓰기 IOPS 한계에 닿거나 백업·VACUUM 시간이 감당이 안 될 때.

얻는 것

  • 저장 용량과 쓰기 처리량이 샤드 수만큼 늘어난다.
  • 리다이렉트는 키로만 조회하므로 scatter-gather 가 없다.

대가

  • 키 외 조회 (사용자별 링크 목록) 는 모든 샤드를 뒤져야 한다. user_id → short_key 인덱스 테이블을 따로 두거나 Step 10 의 분석 DB 로 넘긴다.
  • 리샤딩이 어렵다. 처음부터 가상 샤드 (예: 1024개) 를 물리 노드에 매핑해 두면 노드 추가가 매핑 변경으로 끝난다.
  • 도구: 애플리케이션 라우팅 (ShardingSphere) 또는 Citus / Vitess.

코드에서 바뀌는 것ShardedShortUrlRepository. persistence 어댑터 내부에서만 바뀐다.

Step 9

배포·스케일 단위 분리

도입 · 읽기/쓰기 서비스 분리

넘어가는 신호리다이렉트는 20대가 필요한데 생성은 2대면 충분하고, 생성 쪽 배포가 리다이렉트를 흔들 때.

얻는 것

  • 읽기 서비스는 DB 커넥션을 거의 쓰지 않아 가볍고 많이 띄울 수 있다.
  • 쓰기 서비스 장애가 리다이렉트에 번지지 않는다.
  • 같은 코드베이스를 Spring 프로필로 나눠 배포해도 된다. 레포를 쪼갤 필요는 없다.

대가

  • 운영 대상이 둘로 늘어난다. 공통 도메인 모듈의 버전 관리가 필요하다.

코드에서 바뀌는 것Step 0 에서 나눠 둔 RedirectController 와 UrlController 가 그대로 배포 단위가 된다.

Stage 3 · 분석·글로벌

Step 10

클릭 분석을 비동기로

도입 · Kafka + ClickHouse

넘어가는 신호클릭 통계 요구가 들어왔을 때. 리다이렉트 경로에서 동기 INSERT 하면 p99 가 튀고 DB 쓰기가 100배로 는다.

얻는 것

  • 리다이렉트 지연에 영향이 없다. produce 는 로컬 버퍼에 쌓고 리턴한다.
  • ClickHouse 는 시계열 집계 (일별 클릭, 리퍼러, 국가) 에 맞는 컬럼 DB 다. 운영 DB 와 완전히 분리된다.
  • 실시간 카운터는 컨슈머가 Redis INCR 로.

대가

  • 이벤트 유실을 허용한다 (acks=1, 앱 크래시 시 버퍼 손실). 정확도보다 가용성.
  • Kafka 클러스터 운영 비용. 초기엔 관리형 (MSK, Confluent) 으로.

코드에서 바뀌는 것ClickEventPublisher 포트 1개 추가. ResolveShortUrl 이 302 전에 호출.

Step 11

지리적 확장

도입 · GeoDNS + CDN + 멀티 리전

넘어가는 신호해외 사용자 리다이렉트 지연 200ms 이상, 또는 리전 하나가 죽으면 전면 중단이라는 사실이 불편해질 때.

얻는 것

  • 사용자 근처 리전에서 리다이렉트가 끝난다.
  • 301 응답은 CDN 엣지에 캐시되어 서버까지 오지 않는다. 302 는 안 된다 (통계가 필요하면 302 를 유지).
  • 리전 장애 시 GeoDNS 가 다른 리전으로 돌린다.

대가

  • 생성 직후 다른 리전에서 조회하면 복제 지연에 걸린다. 생성한 리전으로 폴백하거나 몇 초를 허용한다.
  • Snowflake 노드 ID 범위를 리전별로 나눠야 충돌이 없다.
  • 비용이 리전 수에 비례한다.

코드에서 바뀌는 것코드 변경 없음. 노드 ID 범위 설정과 DB 복제 구성.

Step 12

남용 방어

도입 · API Gateway + Safe Browsing

넘어가는 신호봇의 생성 폭주, 피싱 URL 신고. 어느 단계에서든 먼저 올 수 있다.

얻는 것

  • IP · API key 기준 토큰 버킷. 상태는 Redis 에 두어 게이트웨이 여러 대가 공유한다.
  • 악성 판정 시 링크를 비활성화하고 리다이렉트 대신 경고 페이지를 낸다.
  • Step 6 의 없는 키 공격도 여기서 1차로 걸러진다.

대가

  • Safe Browsing 조회는 느리므로 생성 응답을 막지 않고 비동기로. 판정 전 짧은 창이 생긴다.
  • 정상 사용자를 429 로 막는 오탐. 한도와 버스트 값을 트래픽 보고 조정한다.

코드에서 바뀌는 것게이트웨이 설정 + UrlSafetyChecker 포트

System design · URL shortener

URL 단축기 확장 로드맵

스프링 부트 한 대와 해시맵에서 시작해 멀티 리전까지, 기술을 하나씩 들이는 순서다. 각 단계는 바로 앞 단계의 병목 하나를 풀고, 그 기술을 고른 이유와 탈락한 대안을 함께 적었다. 기준 규모는 생성 100 TPS, 리다이렉트 10,000 TPS, 10년 누적 300억 건.

이미 있던 것이 단계에서 새로 들어오는 것
  1. 0인메모리 Map스프링 부트 한 대, 메모리에 저장
  2. 1PostgreSQL + JPA관계형 DB 로 영속화
  3. 2DB 시퀀스 + Base62충돌 없는 키 생성
  4. 3로드밸런서 + 앱 수평 확장앱을 여러 대로
  5. 4Redis 캐시읽기를 DB 에서 떼어 낸다
  6. 5PostgreSQL 읽기 복제본캐시 미스 조회를 분산
  7. 6블룸 필터 + 네거티브 캐시없는 키 공격 방어
  8. 7Snowflake ID 생성기DB 시퀀스 의존 제거
  9. 8DB 샤딩저장소를 수평 분할
  10. 9읽기/쓰기 서비스 분리배포·스케일 단위 분리
  11. 10Kafka + ClickHouse클릭 분석을 비동기로
  12. 11GeoDNS + CDN + 멀티 리전지리적 확장
  13. 12API Gateway + Safe Browsing남용 방어

Stage 0 · 단일 서버

Step 0

스프링 부트 한 대, 메모리에 저장

도입 · 인메모리 Map

넘어가는 신호시작점. 도메인 로직(키 생성·리다이렉트·만료)만 먼저 굳힌다.

얻는 것

  • 생성·리다이렉트 API 와 테스트가 하루 안에 나온다.
  • 이 단계에서 이미 IdGenerator, ShortUrlRepository, ShortUrlCache 포트를 둔다. 이후 모든 단계는 이 세 포트의 구현체만 바꾼다.

대가

  • 프로세스를 재시작하면 전부 사라진다.
  • 인스턴스를 두 대 띄우면 서로의 키를 모른다.

왜 이 기술인가

  • 선택 기준 이 시스템의 병목은 언어가 아니라 DB 와 캐시다. 리다이렉트는 I/O 대기가 전부고 CPU 작업은 Base62 변환 정도라, 언어는 원시 성능보다 이후 12단계에서 붙일 기술의 클라이언트 생태계 로 고른다.
  • JVM (Kotlin + Spring Boot) 을 고른 이유 PostgreSQL (JPA/JDBC), Redis (Lettuce), Kafka, 샤딩 (ShardingSphere), 관측성 (Micrometer), 회로 차단기 (Resilience4j) 까지 전부 성숙한 1급 클라이언트가 있다. Java 21 가상 스레드로 I/O 대기 중 스레드를 묶지 않아 Spring MVC 한 대로 수천 RPS 가 나온다. p99 50ms 요구에는 충분하다.
  • 대안 · Go 메모리가 1/5, 기동 1초, 리다이렉트 서비스 자체로는 가장 적합하다. 대신 ORM·마이그레이션·Kafka 클라이언트 생태계가 얇아 생성·분석 쪽 개발이 느리다. Step 9 에서 읽기 서비스를 분리한 뒤 그 서비스만 Go 로 재작성 하는 선택지로 남긴다.
  • 대안 · Node.js 개발 속도가 빠르고 I/O 모델이 맞다. 다만 타입 안전성과 대규모 운영 도구 (프로파일링, GC 튜닝, 스레드 덤프) 가 JVM 보다 약하고, 멀티코어 활용에 클러스터 모드가 따로 필요하다.
  • 대안 · Rust 성능은 최고지만 개발 속도가 가장 느리고, 이 시스템은 그 성능을 쓸 곳이 없다.
  • Kotlin vs Java null 안전과 data class 로 도메인 코드가 짧아지고, Java 라이브러리를 그대로 쓴다. Java 를 골라도 설계는 같다.
  • Spring Boot vs Ktor / Micronaut / Quarkus Spring 이 위 통합 폭과 운영 사례가 가장 넓다. 기동 시간·메모리가 문제되면 (Step 9 의 읽기 서비스 20대) Quarkus 나 GraalVM native 로 옮길 수 있고, 포트/어댑터 구조라 도메인 코드는 그대로다.
  • Spring MVC vs WebFlux MVC + 가상 스레드. WebFlux 는 JPA 와 맞지 않아 R2DBC 가 필요하고 디버깅이 어렵다. 읽기 서비스가 캐시만 보게 되는 Step 9 이후에야 리액티브 전환의 득이 생긴다.
  • ConcurrentHashMap 으로 시작하는 이유 리포지토리 포트의 가장 작은 구현체다. 키 생성·만료·리다이렉트 규칙을 DB 없이 테스트로 먼저 굳히면, 이후 어댑터 교체 때 도메인이 흔들리지 않는다. 처음부터 DB 를 붙이면 스키마와 JPA 설정이 도메인보다 먼저 온다.
  • 랜덤 키로 시작하는 이유 메모리 단계에선 유일성을 보장할 수단이 없으니 랜덤 + 충돌 재시도가 가장 단순하다. Step 2 에서 교체한다.

코드에서 바뀌는 것InMemoryShortUrlRepository, RandomKeyGenerator (충돌 시 재시도)

Step 1

관계형 DB 로 영속화

도입 · PostgreSQL + JPA

넘어가는 신호첫 실배포. 재시작해도 링크가 살아 있어야 한다.

얻는 것

  • 영속성. 백업과 복구가 가능해진다.
  • short_key UNIQUE 제약이 충돌을 DB 레벨에서 막아 준다.
  • 단일 PostgreSQL 로 읽기 수천 TPS, 쓰기 수백 TPS 까지는 인덱스 조회만으로 버틴다.

대가

  • 모든 리다이렉트가 DB 왕복 1회 (약 1ms).
  • 앱도 DB 도 한 대. 둘 중 하나가 죽으면 서비스 중단.

왜 이 기술인가

  • RDB 를 고른 이유 데이터는 key → value 지만 short_key UNIQUE 제약, 트랜잭션, 시퀀스 (Step 2) 가 필요하다. 이 셋을 공짜로 주는 건 RDB 다.
  • PostgreSQL vs MySQL 둘 다 된다. PostgreSQL 은 시퀀스가 1급 객체 (CREATE SEQUENCE … CACHE) 라 Step 2 와 맞고, 스트리밍 복제 (Step 5) 와 Citus (Step 8) 로 이어지는 확장 경로가 내장이다. MySQL 을 골라도 이 설계는 바뀌지 않는다.
  • 대안 · DynamoDB / Cassandra 키 조회만 하는 이 서비스에 사실 잘 맞는다. 지금 안 쓰는 이유는 이 규모에서 과하고 로컬 개발이 번거롭기 때문이다. Step 8 에서 샤딩이 부담되면 그때 이관하는 선택지로 남긴다.
  • 대안 · MongoDB 문서 모델이 줄 이점이 없다. 필드가 5개뿐이다.
  • JPA vs jOOQ / JdbcTemplate / Exposed 쿼리가 키 조회와 INSERT 두 개뿐이라 뭘 써도 된다. JPA 를 고른 건 엔티티 매핑·Flyway 연동·테스트 슬라이스가 한 번에 갖춰지고, 복잡한 조회가 없어 N+1 같은 함정을 밟을 일이 없어서다. Step 8 샤딩에서 JPA 가 걸림돌이 되면 어댑터 안에서 JDBC 로 내려간다.
  • 개발용 H2 설치 없이 돌아가 첫 단계에 맞다. 방언 차이가 생기는 순간 Testcontainers PostgreSQL 로 바꾼다.

코드에서 바뀌는 것JpaShortUrlRepository 로 교체. 테이블은 short_url(id, short_key, long_url, expires_at, created_at)

Step 2

충돌 없는 키 생성

도입 · DB 시퀀스 + Base62

넘어가는 신호랜덤 키의 충돌 체크 조회가 거슬리기 시작할 때. 사실상 Step 1 직후.

얻는 것

  • 시퀀스는 유일하므로 충돌 체크 조회가 사라진다.
  • 비트 셔플은 전단사 함수라 유일성을 유지한 채 순서만 섞는다. abc123 다음이 abc124 가 아니게 된다.
  • 7자 Base62 는 627 ≈ 3.5조. 하루 1천만 건 생성해도 900년.

대가

  • 생성마다 시퀀스 왕복 1회. 시퀀스를 INCREMENT BY 100 으로 배치 할당하면 줄어든다.
  • 해시 방식과 달리 같은 URL 을 두 번 넣으면 키가 두 개 나온다. 중복 제거가 필요하면 long_url 해시 인덱스를 따로.

왜 이 기술인가

  • DB 시퀀스를 고른 이유 이미 있는 DB 가 유일성을 보장한다. 추가 인프라 0. 앱이 몇 대든 안전하다.
  • 대안 · MD5/SHA 해시 앞 7자 같은 URL 에 같은 키가 나오는 장점이 있지만, 생일 역설로 수십억 건에서 충돌이 잦아져 매번 존재 확인 + 재시도가 필요하다. 쓰기 경로가 느려진다.
  • 대안 · UUID / ULID 충돌은 없지만 Base62 로 22자, 26자다. 7자 요구와 맞지 않는다.
  • 대안 · 랜덤 7자 충돌 확률은 낮지만 0 이 아니라 존재 확인 조회가 사라지지 않는다.
  • Feistel 셔플을 고른 이유 전단사 함수라 유일성이 그대로 유지되고, 비밀 키 하나로 순서만 섞는다. 대안인 랜덤 salt 붙이기 는 길이가 늘고, AES-FF1 (형식 보존 암호) 는 같은 효과에 구현이 무겁다.
  • Base62 를 고른 이유 대소문자 + 숫자만 써서 URL 에 그대로 들어간다. Base64 는 + / 가 URL 에서 문제고, Base58 은 혼동 문자 제거 대신 길이가 는다.

코드에서 바뀌는 것DbSequenceIdGenerator, Base62, FeistelShuffle

Step 3

앱을 여러 대로

도입 · 로드밸런서 + 앱 수평 확장

넘어가는 신호앱 CPU 70% 이상 유지, 또는 배포할 때마다 생기는 다운타임.

얻는 것

  • 앱 단일 장애점 제거. 롤링 배포가 가능해진다.
  • 앱에 세션이 없고 ID 는 DB 시퀀스가 발급하므로 몇 대를 띄워도 키가 겹치지 않는다.

대가

  • 이제 상태를 가진 건 DB 뿐이다. 병목이 DB 로 옮겨 간다.
  • DB 커넥션 수가 앱 대수에 비례해 늘어난다. 커넥션 풀 상한을 잡아야 한다.

왜 이 기술인가

  • L7 로드밸런서를 고른 이유 Step 9 에서 경로 (GET /{key} vs POST /api/urls) 로 서비스를 나눠야 한다. L4 (HAProxy TCP 모드) 는 경로를 못 본다.
  • ALB vs Nginx 클라우드면 ALB. 헬스체크·TLS 종료·오토스케일 연동이 관리형이다. 자체 서버면 Nginx. 둘 중 어느 쪽이든 앱 코드는 동일하다.
  • 대안 · API Gateway 를 지금 rate limit·인증까지 얹은 게이트웨이는 Step 12 의 문제를 풀 때 넣는다. 지금은 분산만 필요하다.
  • 대안 · 앱 수직 확장 더 큰 인스턴스로 버티기. 배포 다운타임과 단일 장애점은 그대로라 미룰 뿐 해결이 아니다.

코드에서 바뀌는 것코드 변경 없음. 인프라만 바뀐다.

Step 4

읽기를 DB 에서 떼어 낸다

도입 · Redis 캐시

넘어가는 신호DB 읽기 CPU 나 커넥션 포화, 리다이렉트 p99 상승. 읽기가 쓰기의 100배이므로 가장 효과가 큰 조치다.

얻는 것

  • 히트율 80~95% 면 DB 읽기가 1/5 ~ 1/20 로 준다. 캐시 히트 지연은 1ms 미만.
  • URL 은 생성 후 바뀌지 않으므로 캐시 불일치 문제가 거의 없다. 만료·삭제 시에만 DEL.

대가

  • Redis 가 죽으면 트래픽이 DB 로 전량 유입된다. DB 가 캐시 없이도 버틸 용량이거나 Step 5 가 먼저 와야 한다.
  • 메모리 비용. 핫셋 20% 기준 하루치면 수십 GB.

왜 이 기술인가

  • Redis 를 고른 이유 캐시만 보면 Memcached 와 같지만, Redis 는 이후 단계에서 계속 재사용된다. 네거티브 캐시 (Step 6), 실시간 카운터 INCR (Step 10), rate limit 상태 (Step 12). 인프라 하나로 네 단계를 덮는다.
  • 대안 · Memcached 멀티스레드라 단순 GET 처리량은 높지만, 복제·클러스터가 없고 자료구조가 문자열뿐이다. 위 재사용이 안 된다.
  • 대안 · 앱 로컬 캐시 (Caffeine) 만 앱 N 대가 각자 미스를 내서 히트율이 낮고 메모리가 N 배다. 다만 Redis 앞에 핫키 전용 2단 캐시로 얹는 건 유효하다.
  • 대안 · CDN 302 는 CDN 이 캐시하지 않는다. 301 로 바꾸면 통계를 잃는다. Step 11 에서 301 링크에만 적용한다.
  • cache-aside + write-through 를 고른 이유 URL 은 생성 후 불변이라 무효화가 거의 없고, 생성 시 미리 써 두면 첫 조회 미스가 사라진다. write-back 은 유실 위험만 더한다.

코드에서 바뀌는 것RedisShortUrlCache 가 NoopShortUrlCache 를 교체. ResolveShortUrl 은 그대로.

Step 5

캐시 미스 조회를 분산

도입 · PostgreSQL 읽기 복제본

넘어가는 신호캐시 미스분과 생성 트래픽만으로도 Primary 가 버겁거나, Redis 장애 시 DB 가 버틸 수 없을 때.

얻는 것

  • 읽기 용량이 Replica 수만큼 늘어난다.
  • Primary 장애 시 Replica 를 승격해 복구 시간을 줄인다.

대가

  • 복제 지연 수십 ms. 생성 직후 조회는 Step 4 의 write-through 가 가려 준다. 그래도 Replica 에 없으면 Primary 를 한 번 더 조회한다.
  • 쓰기는 여전히 Primary 한 대.

왜 이 기술인가

  • PostgreSQL 스트리밍 복제를 고른 이유 내장 기능이라 소프트웨어 추가가 없다. WAL 기반이라 지연이 수십 ms 수준이다.
  • 대안 · 논리 복제 테이블 단위 선택이 가능하지만 느리고, 전체 복제가 필요한 여기선 이점이 없다.
  • 비동기를 고른 이유 동기 복제는 쓰기마다 Replica 응답을 기다려 지연이 는다. 가용성 > 일관성이 요구사항이고, 생성 직후 조회는 캐시가 받는다.
  • 왜 Step 4 (Redis) 가 먼저였나 읽기 100:1 에서 캐시는 DB 읽기를 1/10 이하로 줄인다. Replica 는 남은 미스 트래픽을 나누는 2차 조치다. 순서를 바꾸면 Replica 가 캐시로 잡을 트래픽까지 떠안는다.
  • 자동 failover 는 Patroni 또는 관리형 (RDS Multi-AZ) 으로. 복제 자체와는 별개 결정이다.

코드에서 바뀌는 것라우팅 DataSource. @Transactional(readOnly = true) 면 Replica 로.

Step 6

없는 키 공격 방어

도입 · 블룸 필터 + 네거티브 캐시

넘어가는 신호404 비율 급증과 함께 캐시 히트율이 급락할 때. 없는 키는 캐시에 없으므로 전부 DB 로 가고, 랜덤 키를 쏘면 캐시가 무력화된다.

얻는 것

  • 블룸 필터의 '없음' 판정은 100% 정확하다. 메모리 조회라 DB 도 Redis 도 건드리지 않는다.
  • 네거티브 캐시는 같은 없는 키를 반복해서 두드리는 패턴을 막는다.

대가

  • 블룸 필터는 '있음' 에 오탐이 있다 (1% 설정 시). 오탐분은 뒤 단계로 흘러가므로 문제는 아니다.
  • 키 300억 개·오탐 1% 면 필터가 약 36GB. 전역 하나는 비현실적이므로 Step 8 이후 샤드별로 두거나, 그 전까지는 네거티브 캐시 + Step 12 의 rate limit 조합이 현실적이다.

왜 이 기술인가

  • 먼저 공짜로 되는 것 7자 Base62 형식이 아닌 키는 조회 없이 404. 이것만으로 무작위 문자열 공격의 상당수가 걸러진다.
  • 네거티브 캐시를 고른 이유 Redis 에 이미 있어 추가 인프라 0. 같은 없는 키를 반복해서 두드리는 패턴에 효과적이다.
  • 블룸 필터를 더한 이유 공격자가 매번 새 키를 쓰면 네거티브 캐시는 무력하다. 블룸 필터는 키당 약 10 bit 로 '없음' 을 확정한다. 네트워크 왕복 없이 메모리에서 끝난다.
  • 어디에 두나 앱 메모리 (Guava BloomFilter) 는 가장 빠르지만 인스턴스마다 동기화해야 한다. RedisBloom 모듈에 두면 공유되지만 왕복이 생긴다. 키가 수억 개를 넘기 전까진 앱 메모리 + 주기적 재구성이 단순하다.
  • 대안 · rate limit 만 정상 사용자와 공격자를 IP 로만 가르면 오탐이 많다. Step 12 에서 1차 방어로 넣되, 여기 조치와 겹쳐 쓴다.

코드에서 바뀌는 것ShortUrlCache.putNegative(), KeyExistenceFilter 포트

Stage 2 · 쓰기·저장 확장

Step 7

DB 시퀀스 의존 제거

도입 · Snowflake ID 생성기

넘어가는 신호생성 TPS 가 올라 시퀀스 왕복이 쓰기 지연의 주요 부분이 되었거나, Step 8 샤딩 준비 (샤드마다 시퀀스면 유일성이 깨진다).

얻는 것

  • ID 생성이 네트워크 없이 끝난다. 쓰기 경로가 DB 왕복 1회로 준다.
  • 시간순 정렬이 되어 인덱스 삽입이 순차적이다.
  • 노드 ID 배정은 ZooKeeper/etcd 또는 K8s StatefulSet ordinal 로.

대가

  • 표준 64bit 는 Base62 로 11자다. 7자를 유지하려면 비트를 줄인 변형 (예: 초 단위 30bit + 노드 6bit + 시퀀스 6bit = 42bit) 을 쓰거나, 사전 발급 키 풀 (KGS) 로 간다.
  • 시계 역행 시 중복 위험. 역행 감지 시 대기하거나 예외.

왜 이 기술인가

  • Snowflake 를 고른 이유 앱이 로컬에서 생성한다. 네트워크 0, 외부 서비스 0. 시간순이라 B-tree 인덱스 삽입이 순차적이다. 샤드가 늘어도 유일하다.
  • 대안 · KGS (사전 발급 키 풀) 7자를 정확히 보장하고 키가 완전 랜덤이라 가장 깔끔하다. 대신 KGS 자체가 서비스라 HA·키 풀 고갈·인스턴스별 배치 관리가 따라온다. '정확히 7자' 요구가 강하면 이쪽.
  • 대안 · UUIDv7 / ULID 시간순·무충돌이지만 128 bit 라 22자 이상. 탈락.
  • 대안 · DB 시퀀스 배치 할당 유지 Step 8 샤딩 후 샤드마다 시퀀스면 유일성이 깨진다. 전역 시퀀스 DB 를 따로 두면 그게 단일 장애점이다.
  • 노드 ID 배정 ZooKeeper / etcd 가 정석이지만 K8s StatefulSet 이면 ordinal 을 그대로 쓸 수 있어 추가 인프라가 없다.

코드에서 바뀌는 것SnowflakeIdGenerator 가 DbSequenceIdGenerator 를 교체.

Step 8

저장소를 수평 분할

도입 · DB 샤딩

넘어가는 신호단일 PostgreSQL 이 수 TB 를 넘고, 쓰기 IOPS 한계에 닿거나 백업·VACUUM 시간이 감당이 안 될 때.

얻는 것

  • 저장 용량과 쓰기 처리량이 샤드 수만큼 늘어난다.
  • 리다이렉트는 키로만 조회하므로 scatter-gather 가 없다.

대가

  • 키 외 조회 (사용자별 링크 목록) 는 모든 샤드를 뒤져야 한다. user_id → short_key 인덱스 테이블을 따로 두거나 Step 10 의 분석 DB 로 넘긴다.
  • 리샤딩이 어렵다. 처음부터 가상 샤드 (예: 1024개) 를 물리 노드에 매핑해 두면 노드 추가가 매핑 변경으로 끝난다.
  • 도구: 애플리케이션 라우팅 (ShardingSphere) 또는 Citus / Vitess.

왜 이 기술인가

  • 해시 샤딩을 고른 이유 범위 샤딩은 최신 키가 한 샤드에 몰린다 (핫스팟). 해시는 균등 분산되고, 리다이렉트는 항상 키로 조회하므로 범위 스캔이 필요 없다.
  • 애플리케이션 레벨 라우팅을 고른 이유 로직이 hash % N 한 줄이라 미들웨어가 주는 이점이 작고, PostgreSQL 운영 경험을 그대로 쓴다. ShardingSphere 같은 라이브러리를 써도 되지만 필수는 아니다.
  • 대안 · Citus PostgreSQL 확장이라 앱은 투명하지만 코디네이터가 병목이 되고 운영 난이도가 높다. 조인·집계가 많은 워크로드용이다. 여기는 키 조회뿐이다.
  • 대안 · DynamoDB 이관 샤딩을 DB 가 알아서 한다. 운영 인력이 적으면 이쪽이 현실적이다. 포기하는 건 트랜잭션과 UNIQUE 제약인데, 이 서비스는 조건부 쓰기 (attribute_not_exists) 로 대체 가능하다.
  • 가상 샤드를 고른 이유 물리 노드 수로 나누면 노드 추가 시 전체 재분배다. 1024 개 가상 샤드를 노드에 매핑하면 노드 추가는 매핑 변경과 일부 샤드 이동으로 끝난다.

코드에서 바뀌는 것ShardedShortUrlRepository. persistence 어댑터 내부에서만 바뀐다.

Step 9

배포·스케일 단위 분리

도입 · 읽기/쓰기 서비스 분리

넘어가는 신호리다이렉트는 20대가 필요한데 생성은 2대면 충분하고, 생성 쪽 배포가 리다이렉트를 흔들 때.

얻는 것

  • 읽기 서비스는 DB 커넥션을 거의 쓰지 않아 가볍고 많이 띄울 수 있다.
  • 쓰기 서비스 장애가 리다이렉트에 번지지 않는다.
  • 같은 코드베이스를 Spring 프로필로 나눠 배포해도 된다. 레포를 쪼갤 필요는 없다.

대가

  • 운영 대상이 둘로 늘어난다. 공통 도메인 모듈의 버전 관리가 필요하다.

왜 이 기술인가

  • 서비스 분리를 고른 이유 읽기:쓰기 = 100:1 로 트래픽이 비대칭이다. 한 덩어리면 20 대 모두가 쓰기용 DB 커넥션 풀을 들고 있고, 생성 쪽 배포가 리다이렉트를 흔든다.
  • 왜 마이크로서비스 전환이 아닌가 같은 코드베이스를 Spring 프로필로 두 가지 배포 단위로 나눈다. 레포·팀·도메인 분리 비용 없이 스케일 단위만 나눈다. 더 쪼갤 이유가 생기면 그때.
  • 대안 · 한 서비스 + 오토스케일 대수는 맞출 수 있지만 장애 격리가 안 된다. 생성 경로의 DB 장애가 리다이렉트 스레드 풀을 막는다.
  • Step 0 의 컨트롤러 분리가 전제 처음부터 RedirectController 와 UrlController 를 나눠 두어 여기서 코드 변경이 거의 없다.

코드에서 바뀌는 것Step 0 에서 나눠 둔 RedirectController 와 UrlController 가 그대로 배포 단위가 된다.

Stage 3 · 분석·글로벌

Step 10

클릭 분석을 비동기로

도입 · Kafka + ClickHouse

넘어가는 신호클릭 통계 요구가 들어왔을 때. 리다이렉트 경로에서 동기 INSERT 하면 p99 가 튀고 DB 쓰기가 100배로 는다.

얻는 것

  • 리다이렉트 지연에 영향이 없다. produce 는 로컬 버퍼에 쌓고 리턴한다.
  • ClickHouse 는 시계열 집계 (일별 클릭, 리퍼러, 국가) 에 맞는 컬럼 DB 다. 운영 DB 와 완전히 분리된다.
  • 실시간 카운터는 컨슈머가 Redis INCR 로.

대가

  • 이벤트 유실을 허용한다 (acks=1, 앱 크래시 시 버퍼 손실). 정확도보다 가용성.
  • Kafka 클러스터 운영 비용. 초기엔 관리형 (MSK, Confluent) 으로.

왜 이 기술인가

  • Kafka 를 고른 이유 초당 수만 이벤트를 순차 append 로 받고, 파티션으로 컨슈머를 병렬화하고, 보존 기간 안에서 재처리가 된다. 컨슈머 버그로 집계가 틀려도 다시 돌릴 수 있다.
  • 대안 · RabbitMQ 메시지 단위 ack 모델이라 처리량이 낮고 재생이 안 된다. 작업 큐에 맞지 이벤트 스트림엔 맞지 않다.
  • 대안 · Kinesis Kafka 와 같은 모델의 관리형. AWS 라면 운영 부담이 적어 합리적이다. 종속이 싫으면 MSK.
  • 대안 · Redis Streams 소규모엔 충분하고 인프라 추가가 없다. 보존·파티션이 약해 수만 TPS 에선 한계. 초기엔 이걸로 시작해도 된다.
  • 대안 · 직접 ClickHouse INSERT ClickHouse 는 소량 INSERT 에 약하고, 장애 시 리다이렉트 경로로 지연이 번진다. 큐가 완충재다.
  • ClickHouse 를 고른 이유 컬럼 저장 + 압축으로 시계열 GROUP BY 가 빠르고 자체 운영이 가능하다. BigQuery / Redshift 는 관리형이라 편하지만 쿼리당 과금과 종속. Elasticsearch 는 집계가 비싸고 저장이 크다. PostgreSQL 그대로 는 수십억 행 집계가 안 된다.

코드에서 바뀌는 것ClickEventPublisher 포트 1개 추가. ResolveShortUrl 이 302 전에 호출.

Step 11

지리적 확장

도입 · GeoDNS + CDN + 멀티 리전

넘어가는 신호해외 사용자 리다이렉트 지연 200ms 이상, 또는 리전 하나가 죽으면 전면 중단이라는 사실이 불편해질 때.

얻는 것

  • 사용자 근처 리전에서 리다이렉트가 끝난다.
  • 301 응답은 CDN 엣지에 캐시되어 서버까지 오지 않는다. 302 는 안 된다 (통계가 필요하면 302 를 유지).
  • 리전 장애 시 GeoDNS 가 다른 리전으로 돌린다.

대가

  • 생성 직후 다른 리전에서 조회하면 복제 지연에 걸린다. 생성한 리전으로 폴백하거나 몇 초를 허용한다.
  • Snowflake 노드 ID 범위를 리전별로 나눠야 충돌이 없다.
  • 비용이 리전 수에 비례한다.

왜 이 기술인가

  • GeoDNS (Route 53 latency routing) 를 고른 이유 클라이언트 변경 없이 DNS 응답만으로 가까운 리전을 고른다. 가장 단순한 멀티 리전 진입점이다.
  • 대안 · Anycast (Cloudflare, Global Accelerator) failover 가 DNS TTL 에 묶이지 않아 더 빠르다. 비용과 종속이 늘어난다. 리전 장애 시 수십 초가 문제가 되면 이쪽.
  • 비동기 리전 간 복제를 고른 이유 동기는 리전 간 왕복 100 ms 이상이 모든 쓰기에 붙는다. URL 은 불변이라 양쪽에서 동시에 같은 키를 쓰는 충돌이 없다 (Snowflake 노드 범위 분리). Active-Active 가 성립한다.
  • 대안 · 글로벌 DB (Aurora Global, Spanner, CockroachDB) 복제를 DB 가 맡아 운영이 준다. 비용과 종속이 크다. 샤드가 많아 자체 복제 관리가 버거워지면 고려.
  • CDN 은 301 에만 302 는 엣지가 캐시하지 않는다. 통계가 필요 없는 링크만 301 로 내려 엣지에서 끝낸다.

코드에서 바뀌는 것코드 변경 없음. 노드 ID 범위 설정과 DB 복제 구성.

Step 12

남용 방어

도입 · API Gateway + Safe Browsing

넘어가는 신호봇의 생성 폭주, 피싱 URL 신고. 어느 단계에서든 먼저 올 수 있다.

얻는 것

  • IP · API key 기준 토큰 버킷. 상태는 Redis 에 두어 게이트웨이 여러 대가 공유한다.
  • 악성 판정 시 링크를 비활성화하고 리다이렉트 대신 경고 페이지를 낸다.
  • Step 6 의 없는 키 공격도 여기서 1차로 걸러진다.

대가

  • Safe Browsing 조회는 느리므로 생성 응답을 막지 않고 비동기로. 판정 전 짧은 창이 생긴다.
  • 정상 사용자를 429 로 막는 오탐. 한도와 버스트 값을 트래픽 보고 조정한다.

왜 이 기술인가

  • API Gateway 를 고른 이유 rate limit·WAF·인증을 앱 밖에서 한곳에 모은다. 앱은 비즈니스 로직만 남는다. Kong, Envoy, AWS API Gateway 중 운영 환경에 맞는 것.
  • 대안 · 앱 안에서 Bucket4j 간단하지만 인스턴스별 한도라 20 대면 실효 한도가 20 배다. Redis 백엔드를 붙이면 되지만 그 시점엔 게이트웨이가 낫다.
  • 대안 · Nginx limit_req IP 기준만 가능하고 API key·사용자 단위 한도를 못 건다.
  • 토큰 버킷을 고른 이유 짧은 버스트를 허용하면서 평균을 제한한다. 고정 윈도우는 경계에서 2 배가 새고, 슬라이딩 로그는 메모리가 크다.
  • Safe Browsing API 를 고른 이유 자체 블랙리스트는 커버리지가 없다. Google 이 유지하는 목록을 쓰는 게 현실적. VirusTotal 은 호출 한도가 빡빡하고, 자체 ML 은 이 규모에서 과하다.
  • 비동기 검사를 고른 이유 외부 API 지연을 생성 응답에 얹지 않는다. 판정 전 수 초의 창은 받아들이고, 악성 판정 시 사후 비활성화한다.

코드에서 바뀌는 것게이트웨이 설정 + UrlSafetyChecker 포트

3로드밸런서 + 앱 수평 확장앱 CPU 70% 이상 유지, 또는 배포할 때마다 생기는 다운타임.Step 9 경로 라우팅 대비 L7코드 변경 없음. 인프라만 바뀐다.
4Redis 캐시DB 읽기 CPU 나 커넥션 포화, 리다이렉트 p99 상승.이후 4단계에서 재사용RedisShortUrlCache 가 NoopShortUrlCache 를 교체. ResolveShortUrl 은 그대로.
5PostgreSQL 읽기 복제본캐시 미스분과 생성 트래픽만으로도 Primary 가 버겁거나, Redis 장애 시 DB 가 버틸 수 없을 때.내장 기능, 비동기로 가용성 우선라우팅 DataSource. @Transactional(readOnly = true) 면 Replica 로.
6블룸 필터 + 네거티브 캐시404 비율 급증과 함께 캐시 히트율이 급락할 때.없음 판정 확정, 메모리로 끝ShortUrlCache.putNegative(), KeyExistenceFilter 포트
7Snowflake ID 생성기생성 TPS 가 올라 시퀀스 왕복이 쓰기 지연의 주요 부분이 되었거나, Step 8 샤딩 준비 (샤드마다 시퀀스면 유일성이 깨진다).로컬 생성, 샤딩 후에도 유일SnowflakeIdGenerator 가 DbSequenceIdGenerator 를 교체.
8DB 샤딩단일 PostgreSQL 이 수 TB 를 넘고, 쓰기 IOPS 한계에 닿거나 백업·VACUUM 시간이 감당이 안 될 때.키 조회만이라 해시 + 가상 샤드ShardedShortUrlRepository. persistence 어댑터 내부에서만 바뀐다.
9읽기/쓰기 서비스 분리리다이렉트는 20대가 필요한데 생성은 2대면 충분하고, 생성 쪽 배포가 리다이렉트를 흔들 때.100:1 비대칭 트래픽Step 0 에서 나눠 둔 RedirectController 와 UrlController 가 그대로 배포 단위가 된다.
10Kafka + ClickHouse클릭 통계 요구가 들어왔을 때.재처리 가능한 스트림 + 컬럼 DBClickEventPublisher 포트 1개 추가. ResolveShortUrl 이 302 전에 호출.
11GeoDNS + CDN + 멀티 리전해외 사용자 리다이렉트 지연 200ms 이상, 또는 리전 하나가 죽으면 전면 중단이라는 사실이 불편해질 때.불변 데이터라 비동기 Active-Active코드 변경 없음. 노드 ID 범위 설정과 DB 복제 구성.

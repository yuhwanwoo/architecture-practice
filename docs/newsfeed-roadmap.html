뉴스피드 확장 로드맵

조인 쿼리 하나로 피드를 만드는 서버 한 대에서 시작해, 피드를 미리 배달하는 구조로 바꾸고, 셀럽·랭킹·멀티 리전까지 기술을 하나씩 들이는 순서다. 각 단계는 앞 단계의 병목 하나를 풀고, 고른 이유와 탈락한 대안을 함께 적었다. 기준 규모는 DAU 1천만, 피드 조회 피크 6,000 QPS, 게시 23 TPS, 평균 팔로워 200명.

이미 있던 것이 단계에서 새로 들어오는 것
  1. 0Spring Boot + PostgreSQL · pull 모델조인 한 번으로 피드를 만든다
  2. 1객체 저장소 (S3) + CDN + presigned URL이미지를 앱 밖으로
  3. 2로드밸런서 + 앱 수평 확장앱을 여러 대로
  4. 3PostgreSQL 읽기 복제본피드 조회를 Primary 에서 뗀다
  5. 4Redis 피드 리스트 · fan-out on write조회 시 조인 대신 게시 시 배달
  6. 5Redis 게시물·사용자 캐시 (MGET hydrate)ID 20개를 본문으로
  7. 6Kafka + fan-out 워커배달을 게시 요청에서 뗀다
  8. 7하이브리드 (셀럽은 pull)팔로워 100만 명 문제
  9. 8DB 샤딩 (posts · follows)수십억 행을 나눈다
  10. 9랭킹 (피처 저장소 + 배치)시간순에서 점수순으로
  11. 10Redis 카운터 + 이벤트 원장좋아요 수를 DB 에서 뗀다
  12. 11미디어 처리 워커 (libvips)이 시스템의 유일한 CPU 바운드 구간
  13. 12GeoDNS + 멀티 리전 + API Gateway지리적 확장과 남용 방어

Stage 0 · 단일 서버

Step 0

조인 한 번으로 피드를 만든다

도입 · Spring Boot + PostgreSQL · pull 모델

넘어가는 신호시작점. 게시·팔로우·피드 세 유스케이스를 가장 단순한 저장 구조로 굳힌다.

얻는 것

  • 테이블 세 개 (users, follows, posts) 와 쿼리 하나로 전체 기능이 돈다.
  • 게시물 ID 를 시간순 정렬 가능한 64bit (Snowflake 류) 로 발급해 커서 페이지네이션을 처음부터 쓴다. OFFSET 은 깊어질수록 느려진다.
  • 이 단계에서 PostRepository, FollowRepository, FeedSource, PostCache, FanoutPublisher, MediaStore 포트를 둔다. 이후 모든 단계는 구현체만 바꾼다.

대가

  • 피드 쿼리 비용이 팔로우 수에 비례한다. 팔로우 500명이면 500명의 최신 글을 모아 정렬해야 한다. 팔로우가 많은 사용자부터 느려진다.
  • 이미지가 아직 DB 나 앱 디스크에 있다. 다음 단계에서 바로 뺀다.

왜 이 기술인가

  • 언어·프레임워크 URL 단축기와 같은 결정이다. 뉴스피드도 I/O 바운드다. 피드 조회는 Redis·DB 응답 대기가 전부이고 CPU 는 JSON 직렬화 정도다. 그래서 원시 성능이 아니라 이후 12단계의 통합 폭과 인력으로 JVM + Spring Boot 를 고른다. 예외가 하나 있는데 Step 11 의 이미지 처리다. 그건 CPU 바운드라 앱 밖으로 뺀다.
  • PostgreSQL 을 고른 이유 초기 데이터 모델이 관계형이다. 팔로우는 다대다, 피드는 조인. 외래 키·유니크 제약·트랜잭션이 바로 필요하다.
  • 대안 · Cassandra / DynamoDB 로 시작 타임라인 저장에는 잘 맞지만 Step 0 의 조인 쿼리를 못 쓴다. 처음부터 fan-out 을 짜야 해서 시작 비용이 크다. Step 8 에서 피드 영속화가 필요해지면 재고한다.
  • 대안 · 그래프 DB (Neo4j) 팔로우 그래프 탐색에 좋아 보이지만 피드는 2홉 이상 탐색이 없다. 1홉 조인이면 RDB 가 더 빠르고 운영이 쉽다.
  • pull 모델로 시작하는 이유 가장 단순하고 저장 공간이 최소다. 팔로우 수가 적을 때는 조인 쿼리가 수 ms 다. fan-out 은 Step 4 에서 이 쿼리가 실제로 느려지는 걸 측정한 뒤 넣는다. 처음부터 push 로 가면 Redis·큐·워커가 Step 0 에 들어와 측정할 기준점이 없다.
  • 시간순 정렬 ID 를 처음부터 쓰는 이유 커서 페이지네이션 (WHERE id < :cursor ORDER BY id DESC LIMIT 20) 은 인덱스 한 번으로 끝나고, Step 4 의 Redis 리스트에서도 ID 만으로 정렬·머지가 된다. OFFSET 은 페이지가 깊어질수록 건너뛴 행을 전부 읽는다. UUIDv7 또는 Snowflake 변형이면 된다.

코드에서 바뀌는 것GetHomeFeed 가 FeedSource 포트를 호출하고, 구현은 PullFeedSource (조인 쿼리). FanoutPublisher 는 아직 Noop.

Step 1

이미지를 앱 밖으로

도입 · 객체 저장소 (S3) + CDN + presigned URL

넘어가는 신호업로드 트래픽이 앱 서버 대역폭과 디스크를 잡아먹고, 이미지 응답이 피드 API 의 지연을 끌어올릴 때. 사실상 Step 0 직후.

얻는 것

  • 앱 서버가 바이너리를 만지지 않는다. 업로드 200KB × 초당 수백 건이 앱을 거치지 않는다.
  • 하루 400GB 의 미디어가 DB 와 분리된다. DB 는 메타데이터 1KB 만 받는다.
  • CDN 캐시 히트가 90% 이상이면 원본 저장소 트래픽은 1/10.

대가

  • 업로드가 2단계 (presign → PUT) 로 늘어 클라이언트가 복잡해진다.
  • 업로드만 하고 게시를 안 한 고아 객체가 생긴다. 수명 주기 정책으로 24시간 뒤 삭제.

왜 이 기술인가

  • 객체 저장소를 고른 이유 이미지는 불변·대용량·순차 읽기다. 블록 저장소나 DB 가 아니라 객체 저장소의 설계 목적 그대로다. GB 당 월 2센트대로 가장 싸고 내구성이 11 nines 다.
  • 대안 · DB 에 BLOB 백업·복제·VACUUM 이 전부 이미지 크기만큼 느려진다. 하루 400GB 면 DB 가 일주일 만에 TB 를 넘는다.
  • 대안 · 앱 서버 디스크 수평 확장 (Step 2) 과 양립하지 않는다. 어느 서버에 있는지 찾아야 한다.
  • presigned URL 을 고른 이유 앱 서버를 거치는 업로드는 대역폭·메모리·커넥션을 바이너리 크기만큼 쓴다. 서명된 URL 은 권한 검사만 앱이 하고 바이트는 클라이언트와 저장소 사이에서 직접 흐른다. 대안인 앱 프록시 업로드 는 바이러스 검사 등 즉시 처리가 필요할 때만 선택한다.
  • CDN 을 지금 넣는 이유 이미지는 302 와 달리 캐시 가능한 정적 자원이고, 피드 한 화면에 20장이 뜬다. 피드 API 1건에 이미지 요청 20건이 따라오므로 CDN 없이는 저장소 트래픽이 API 의 20배다. CloudFront / Cloudflare 어느 쪽이든 된다.

코드에서 바뀌는 것MediaStore 포트의 구현 S3MediaStore (presign 발급). PublishPost 는 URL 만 받는다.

Stage 1 · 읽기 확장

Step 2

앱을 여러 대로

도입 · 로드밸런서 + 앱 수평 확장

넘어가는 신호앱 CPU 70% 이상, 배포 다운타임. 피크 6,000 QPS 를 2 vCPU 한 대가 못 받는다.

얻는 것

  • 앱 단일 장애점 제거, 롤링 배포.
  • 인증을 JWT 로 두어 세션 저장소 없이 무상태를 유지한다.

대가

  • 병목이 DB 로 옮겨 간다. 피드 조인 쿼리가 앱 대수만큼 DB 를 두드린다.
  • 커넥션 수가 대수에 비례. 풀 상한을 잡는다.

왜 이 기술인가

  • L7 로드밸런서 URL 단축기와 같다. 이후 경로별 라우팅과 헬스체크가 필요하다.
  • JWT 로 무상태를 만드는 이유 세션을 서버 메모리에 두면 같은 서버로만 가야 한다 (sticky session). 세션 저장소 (Redis) 를 두는 것도 방법이지만 Step 4 전까지 Redis 를 들이지 않으려면 JWT 가 가장 얇다. 로그아웃·폐기가 필요해지면 짧은 만료 + 리프레시 토큰으로 푼다.
  • 대안 · 수직 확장 더 큰 인스턴스. 배포 다운타임과 단일 장애점이 그대로다.

코드에서 바뀌는 것코드 변경 없음. Actuator 헬스체크와 graceful shutdown 설정만.

Step 3

피드 조회를 Primary 에서 뗀다

도입 · PostgreSQL 읽기 복제본

넘어가는 신호Primary CPU 가 피드 조인 쿼리로 포화. 읽기 : 쓰기 = 100 : 1 이라 복제본이 바로 효과를 낸다.

얻는 것

  • 읽기 용량이 Replica 수만큼 는다. 쓰기 23 TPS 는 Primary 혼자 충분하다.

대가

  • 복제 지연 수십 ms. 내가 방금 쓴 글이 내 피드에 안 보이는 창이 생긴다. 작성자 본인 피드는 Primary 를 읽거나 방금 쓴 글을 클라이언트가 끼워 넣는다.
  • 근본 문제인 팔로우 수 비례 비용은 그대로다. Replica 를 늘려도 쿼리 하나의 지연은 안 줄어든다.

왜 이 기술인가

  • Replica 를 캐시보다 먼저 넣는 이유 URL 단축기와 순서가 다르다. 단축기는 키 → URL 이라 캐시 한 줄로 끝났지만, 피드 결과는 사용자마다 다르고 매 요청 바뀌어 결과 캐시 히트율이 낮다. 지금 병목은 '조인 쿼리 QPS' 이고 그걸 가장 싸게 늘리는 게 Replica 다.
  • 대안 · 피드 결과 캐시 (사용자별 결과를 60초 캐시) 효과는 있지만 새 글이 60초 늦게 보이고, 활성 사용자 비율이 낮으면 히트율이 떨어진다. Step 4 의 fan-out 이 같은 문제를 구조적으로 풀므로 임시방편은 건너뛴다.
  • 비동기 복제 동기는 쓰기 지연을 늘리고, 요구사항이 최종 일관성이다. 작성자 본인 피드의 read-your-writes 는 애플리케이션에서 처리한다.

코드에서 바뀌는 것라우팅 DataSource. @Transactional(readOnly = true) 면 Replica.

Stage 2 · 피드 구조 전환

Step 4

조회 시 조인 대신 게시 시 배달

도입 · Redis 피드 리스트 · fan-out on write

넘어가는 신호팔로우 300명 이상 사용자의 피드 p99 가 500ms 를 넘고, Replica 를 늘려도 안 내려올 때. 쿼리 자체가 문제다.

얻는 것

  • 피드 조회가 LRANGE 한 번, 1ms 미만. 팔로우 수와 무관해진다.
  • 읽기 100 : 쓰기 1 비율을 활용한다. 비싼 일을 적게 일어나는 쪽 (게시) 으로 옮긴다.
  • 리스트는 ID 만 1,000개로 자른다. 사용자당 8KB, DAU 1천만이면 80GB.

대가

  • 게시 비용이 팔로워 수에 비례한다. 팔로워 200명이면 Redis 쓰기 200번. 셀럽은 Step 7 까지 문제로 남는다.
  • Redis 피드는 휘발성이다. 비우면 Step 0 의 pull 로 재구성한다. pull 경로를 없애지 않는 이유다.
  • 언팔로우·삭제 시 피드에서 빼는 작업이 필요하다. 조회 시 필터링으로 느슨하게 처리한다.

왜 이 기술인가

  • fan-out on write 를 고른 이유 읽기 : 쓰기 = 100 : 1 이면 비싼 계산을 쓰기 쪽으로 옮기는 게 총비용이 100배 싸다. 트위터·인스타그램이 같은 이유로 같은 구조다.
  • Redis 리스트를 고른 이유 피드는 '사용자별 최근 N개 ID' 다. LPUSH + LTRIM 으로 O(1) 삽입과 상한 유지가 되고 LRANGE 조회가 1ms 미만이다. 메모리 상주라 fan-out 의 초당 수만 쓰기를 받는다.
  • 대안 · DB 에 feed 테이블 (user_id, post_id) 하루 4억 행 INSERT 와 그만큼의 삭제. 디스크 기반 DB 에서 쓰기 증폭이 감당 안 된다. 인덱스가 끝없이 자란다.
  • 대안 · Cassandra 타임라인 테이블 쓰기에 강하고 영속적이라 유력하다. 지금 안 쓰는 이유는 운영 대상을 하나 더 늘리기 때문이고, Redis 는 Step 5·10 에서 재사용된다. 피드를 영속화해야 할 때 (비활성 사용자 피드 보존) 재고한다.
  • 리스트 vs ZSET ZSET 은 점수 (시간) 로 정렬·중복 제거가 되지만 메모리가 2배다. 시간순 ID 를 쓰면 리스트로 충분하고, Step 6 의 중복 삽입 문제가 커지면 ZSET 으로 바꾼다.
  • 1,000개로 자르는 이유 사용자가 피드를 1,000개 넘게 내려 보는 일은 거의 없다. 그 너머는 pull 폴백. DAU 1천만 × 8KB = 80GB 로 Redis 클러스터 몇 대 안에 들어온다.

코드에서 바뀌는 것FeedSource 구현을 RedisFeedSource 로. FanoutPublisher 구현 SyncRedisFanout. pull 구현은 폴백으로 남긴다.

Step 5

ID 20개를 본문으로

도입 · Redis 게시물·사용자 캐시 (MGET hydrate)

넘어가는 신호피드 ID 는 Redis 에서 받는데 본문 20개를 채우느라 DB 조회가 요청당 20번. Replica 읽기 QPS 가 피드 QPS 의 20배가 될 때.

얻는 것

  • 요청당 Redis 왕복 2회 (피드 + MGET), DB 는 캐시 미스분만 IN 쿼리 1회.
  • 최근 글일수록 많이 읽히므로 히트율이 높다. 24시간 TTL 에 95% 이상.

대가

  • 게시물 수정·삭제 시 캐시 무효화. 게시물은 거의 불변이라 DEL 하나로 끝난다.
  • 좋아요 수처럼 자주 바뀌는 필드를 캐시에 넣으면 무효화가 잦다. Step 10 에서 분리한다.

왜 이 기술인가

  • 게시물 캐시를 Step 4 다음에 넣는 이유 Step 4 가 피드 ID 조회를 Redis 로 옮기면서 DB 부하의 성격이 바뀐다. 조인 1번이 ID 조회 20번으로 바뀌어 QPS 가 20배 된다. 캐시 없이는 Step 4 가 DB 를 더 괴롭힌다.
  • MGET 을 쓰는 이유 20번 왕복을 1번으로. Redis 왕복 0.3ms × 20 = 6ms 가 0.5ms 로 준다. 파이프라이닝과 같은 효과.
  • 해시 vs 직렬화 문자열 게시물 전체를 JSON 문자열 하나로 두면 MGET 한 번으로 끝난다. 필드 단위 갱신이 필요하면 해시. 게시물은 불변에 가까워 문자열로 시작한다.
  • 대안 · 앱 로컬 캐시 (Caffeine) 인기 글 상위 1% 는 모든 인스턴스가 같은 걸 읽으므로 Redis 앞에 로컬 캐시를 얹으면 효과가 크다. 다만 인스턴스마다 무효화가 안 되니 TTL 을 짧게 (10초) 둔다. Redis 다음에 추가한다.

코드에서 바뀌는 것PostCache 구현 RedisPostCache. GetHomeFeed 의 hydrate 단계가 PostCache.getAll(ids) 를 거친다.

Step 6

배달을 게시 요청에서 뗀다

도입 · Kafka + fan-out 워커

넘어가는 신호게시 API p99 가 팔로워 수에 비례해 수백 ms 를 넘고, 팔로워 1만 명 계정의 게시가 수 초 걸릴 때. Redis 장애가 게시 실패로 번질 때.

얻는 것

  • 게시 응답이 팔로워 수와 무관해진다. INSERT + produce 로 10ms 안쪽.
  • 워커를 따로 스케일한다. 피크에 밀린 이벤트는 큐에 쌓였다가 처리된다.
  • Redis 장애 시 게시는 성공하고 배달만 지연된다. 재처리가 된다.

대가

  • 피드 반영이 수백 ms ~ 수 초 늦는다. 최종 일관성을 요구사항으로 받아들인 이유다.
  • 워커가 두 번 처리하면 피드에 같은 글이 두 번 들어간다. 멱등 처리 (리스트 삽입 전 존재 확인 또는 ZSET).

왜 이 기술인가

  • 비동기로 가는 이유 동기 fan-out 은 게시 요청의 지연을 팔로워 수가 결정하게 한다. 사용자는 자기 글이 즉시 올라가길 원하지, 200명에게 배달이 끝나길 기다리지 않는다. 최종 일관성을 받아들이면 배달은 뒤에서 해도 된다.
  • Kafka 를 고른 이유 하루 200만 게시 이벤트는 사실 작아서 어떤 큐든 된다. Kafka 를 고른 건 같은 이벤트를 Step 9 (상호작용 로그), Step 10 (좋아요 원장), 알림, 검색 색인이 각자 구독하기 때문이다. 토픽 하나에 컨슈머 그룹 여럿이 붙는 모델이 여기 맞는다.
  • 대안 · SQS / RabbitMQ fan-out 하나만 보면 더 단순하고 운영이 쉽다. 구독자가 하나뿐이고 재처리가 필요 없다면 이쪽. 구독자가 둘이 되는 순간 토픽 복제가 필요해진다.
  • 대안 · DB 아웃박스 폴링 큐 없이 posts 테이블을 워커가 폴링. 인프라 추가가 없지만 지연과 DB 부하가 폴링 주기에 묶인다. 가장 작은 규모에서만.
  • 멱등성 at-least-once 라 같은 이벤트가 두 번 올 수 있다. 피드 삽입 전 post_id 존재 확인, 또는 ZSET 으로 전환.

코드에서 바뀌는 것FanoutPublisher 구현을 KafkaFanoutPublisher 로. 워커는 같은 코드베이스의 별도 프로필.

Step 7

팔로워 100만 명 문제

도입 · 하이브리드 (셀럽은 pull)

넘어가는 신호팔로워 100만 계정 하나가 글을 쓰면 fan-out 쓰기 100만 건, 워커가 수 분 밀리고 Redis 쓰기가 폭주할 때. 상위 0.1% 계정이 fan-out 트래픽의 대부분을 만든다.

얻는 것

  • 팔로워 임계값 (예: 10만) 이상 계정은 fan-out 을 건너뛴다. 쓰기 폭증이 사라진다.
  • 셀럽은 수가 적고 글도 적어 그들의 최근 글은 작은 캐시 하나에 다 들어간다. pull 비용이 상수에 가깝다.

대가

  • 피드 조회가 두 소스를 머지한다. 코드가 복잡해지고 지연이 수 ms 는다.
  • 임계값 근처에서 계정이 모드를 오가면 피드에 빈 구간이 생긴다. 전환 시 한 번 백필한다.

왜 이 기술인가

  • 하이브리드를 고른 이유 팔로워 분포는 극단적으로 치우쳐 있다. 상위 0.1% 계정이 전체 fan-out 쓰기의 대부분을 만든다. 그 계정만 push 에서 빼면 쓰기 폭증의 대부분이 사라지고, 나머지 99.9% 는 push 의 빠른 읽기를 그대로 누린다.
  • 대안 · 전부 pull 로 회귀 Step 0 의 문제로 돌아간다.
  • 대안 · 셀럽 글도 push 하되 워커를 늘린다 100만 쓰기를 더 빨리 할 뿐 비용은 그대로다. 글 하나에 100만 × 8B = 8MB 의 Redis 쓰기, 하루 수백 개 셀럽 글이면 수 GB. 그리고 팔로워 1천만이면 10배다.
  • 임계값 10만은 출발점이다. 'fan-out 1건당 비용 × 팔로워 수' 가 '조회 1건당 pull 비용 × 그 계정 팔로워의 일일 피드 조회 수' 를 넘는 지점이 이론값이다. 측정해서 조정한다.
  • 셀럽 글 캐시 셀럽은 수천 명, 각자 최근 글 50개면 수십만 ID 로 Redis 에 다 들어간다. pull 이라 해도 DB 를 보지 않는다.

코드에서 바뀌는 것GetHomeFeed 가 FeedSource 두 개 (RedisFeedSource, CelebrityPullSource) 를 머지. PublishPost 가 팔로워 수로 fan-out 여부를 결정.

Stage 3 · 저장·랭킹·글로벌

Step 8

수십억 행을 나눈다

도입 · DB 샤딩 (posts · follows)

넘어가는 신호posts 수십억 행, follows 수백억 행. 인덱스가 메모리에 안 들어가고 VACUUM 이 하루를 넘길 때.

얻는 것

  • posts 는 post_id 해시. hydrate 는 항상 ID 로 조회하므로 단일 샤드.
  • follows 는 접근 패턴이 둘이다. fan-out 은 '이 사람의 팔로워', 조회는 '내가 팔로우하는 사람'. follows_by_followee, follows_by_follower 두 테이블에 이중 기록하고 각각 해당 키로 샤딩한다.

대가

  • 이중 기록은 두 샤드에 걸친 쓰기다. 트랜잭션 대신 이벤트로 보정 (최종 일관성).
  • 작성자별 글 목록 (프로필 페이지) 은 post_id 샤딩에서 scatter 다. author_id → post_ids 인덱스 테이블을 따로 둔다.
  • 처음부터 가상 샤드 1024개를 물리 노드에 매핑한다.

왜 이 기술인가

  • 샤딩 키를 두 개로 나누는 이유 posts 와 follows 의 접근 패턴이 다르다. posts 는 ID 로만 조회 (hydrate) 하므로 post_id 해시. follows 는 '누구의 팔로워' 와 '누가 팔로우' 두 방향이라 한 키로는 한쪽이 scatter 다. 이중 기록으로 두 방향 모두 단일 샤드로 만든다. 저장은 2배지만 행이 작다.
  • 대안 · Cassandra 로 이관 와이드 컬럼이 타임라인·팔로우 목록에 자연스럽고 샤딩을 DB 가 한다. 운영 인력이 있으면 유력하다. PostgreSQL 유지의 이유는 트랜잭션과 기존 쿼리 보존이다.
  • 대안 · Citus / Vitess 투명하지만 이중 기록 같은 패턴 분리는 어차피 애플리케이션 결정이다.
  • 해시 vs 범위 post_id 는 시간순이라 범위 샤딩하면 최신 샤드에 쓰기가 몰린다. 해시다.

코드에서 바뀌는 것PostRepository, FollowRepository 구현을 샤드 라우팅 버전으로. 포트 시그니처는 그대로.

Step 9

시간순에서 점수순으로

도입 · 랭킹 (피처 저장소 + 배치)

넘어가는 신호제품 지표. 팔로우가 늘어 시간순 피드에서 사용자가 원하는 글을 놓치고, 체류 시간이 정체될 때. 기술 병목이 아니라 제품 결정이다.

얻는 것

  • 처음엔 가중합 하나다. score = 최신성 × w1 + 친밀도 × w2 + 반응 수 × w3. 모델은 나중이다.
  • 친밀도 (내가 누구 글에 반응했나) 는 일배치로 계산해 Redis 에 둔다. 온라인 경로는 조회와 곱셈만.

대가

  • 후보를 20개가 아니라 500개 가져와야 한다. Redis 피드 길이와 MGET 크기가 는다.
  • 랭킹 서비스가 A/B 테스트와 지표 파이프라인을 요구한다. 작은 팀이면 미룬다.

왜 이 기술인가

  • 가중합으로 시작하는 이유 랭킹의 효과 대부분은 '친밀도 높은 사람 글을 위로' 에서 나온다. 식 하나와 피처 셋으로 그걸 얻고, 모델은 A/B 인프라가 생긴 뒤다.
  • 피처를 배치로 만드는 이유 친밀도는 수개월 상호작용의 집계다. 요청마다 계산할 수 없고 매일 조금 바뀐다. Spark 일배치 → Redis 적재가 가장 단순하다. Flink 실시간은 '방금 반응한 사람' 가중치가 필요해질 때.
  • 대안 · 랭킹을 DB 쿼리로 ORDER BY score 는 후보 전체를 읽어야 한다. 후보를 500개로 제한한 뒤 앱에서 정렬하는 쪽이 싸다.
  • 왜 Step 9 인가 기술 병목이 아니라 제품 요구라 순서가 유연하다. fan-out·캐시가 안정된 뒤에 넣어야 랭킹 효과를 지연 변화와 분리해 측정할 수 있다.

코드에서 바뀌는 것RankingPolicy 포트 추가. 구현 ChronologicalRanking → WeightedRanking.

Step 10

좋아요 수를 DB 에서 뗀다

도입 · Redis 카운터 + 이벤트 원장

넘어가는 신호좋아요 쓰기가 게시 쓰기의 50배. UPDATE posts SET like_count = like_count + 1 이 인기 글 행에서 락 경합을 일으킬 때.

얻는 것

  • INCR 은 원자적이고 1µs 다. 핫 행 락이 사라진다.
  • hydrate 때 카운터를 MGET 으로 함께 읽는다. 게시물 캐시 무효화와 분리된다.

대가

  • Redis 가 데이터를 잃으면 카운터가 어긋난다. 원장에서 재계산할 수 있어야 한다.
  • 중복 좋아요 방지는 SET liked:{post} 또는 DB 유니크 제약. 둘 다 두면 비용이 2배.

왜 이 기술인가

  • Redis 카운터를 고른 이유 좋아요는 쓰기 중 가장 잦고, 인기 글 하나에 몰린다. DB 행 UPDATE 는 같은 행에 락이 직렬화되어 초당 수백 건이 한계다. INCR 은 단일 스레드 Redis 에서도 초당 수십만 건이다.
  • 원장을 따로 두는 이유 카운터는 표시용이고 정합성의 원천이 아니다. '누가 좋아했나' 는 DB 에 있어야 취소·중복 방지·재계산이 된다. Kafka 로 흘려 배치 UPSERT 하면 DB 쓰기가 묶여서 들어간다.
  • 대안 · DB 에 like 행 INSERT 만 하고 count 는 COUNT(*) 인기 글에서 COUNT 가 수백만 행이다. 캐시해도 무효화가 초당 수백 번.
  • 대안 · CRDT 카운터 멀티 리전 (Step 12) 에서 리전별 카운터를 합칠 때 필요해진다. 그 전까지는 과하다.

코드에서 바뀌는 것CounterStore 포트 추가. LikePost 가 INCR + 이벤트 발행.

Step 11

이 시스템의 유일한 CPU 바운드 구간

도입 · 미디어 처리 워커 (libvips)

넘어가는 신호모바일에서 원본 3MB 이미지를 그대로 내려받아 피드 스크롤이 느리고 데이터가 샐 때. 앱 서버에서 리사이즈를 시도하면 CPU 가 I/O 요청 처리를 막는다.

얻는 것

  • 이미지 디코딩·리사이즈·인코딩은 장당 50~300ms CPU 를 쓴다. 이걸 I/O 바운드 앱 서버에서 분리해야 피드 API p99 가 안 흔들린다.
  • 워커는 CPU 코어 수만큼만 병렬로 돌린다. 가상 스레드가 아니라 고정 풀이다.
  • 썸네일·중간·원본 등 4종을 미리 만들어 CDN 에 둔다.

대가

  • 파생본이 준비되기 전 수 초 동안은 원본 또는 플레이스홀더를 보여 준다.
  • 저장 용량이 1.5배.

왜 이 기술인가

  • 워커로 분리하는 이유 이 로드맵에서 유일한 CPU 바운드 작업이다. 이미지 1장 리사이즈는 50~300ms 동안 코어 하나를 꽉 쓴다. I/O 바운드 앱 서버에서 돌리면 그 시간 동안 그 코어가 처리할 수천 건의 피드 요청이 밀린다. 가상 스레드도 도움이 안 된다. CPU 가 바쁜 거지 기다리는 게 아니다.
  • libvips 를 고른 이유 ImageMagick 대비 4~8배 빠르고 메모리 1/10 이다. 스트리밍 처리라 큰 이미지도 메모리에 다 올리지 않는다. imgproxy, Thumbor 같은 기성 서비스가 libvips 위에 있다.
  • 대안 · JVM 에서 ImageIO / Thumbnailator 가능하지만 느리고 (libvips 의 1/5), 포맷 지원 (HEIC, AVIF) 이 약하다. 여기서는 언어를 바꾸는 게 맞다. 워커는 Go 로 짠 imgproxy 를 그대로 쓰거나, JVM 에서 libvips 바인딩을 쓴다.
  • 대안 · 요청 시 변환 (on-the-fly) + CDN 캐시 첫 요청만 변환하고 CDN 이 캐시. 저장이 줄고 해상도 추가가 쉽다. 첫 조회 지연이 수백 ms 라 피드 첫 화면에는 불리하다. 썸네일은 미리, 나머지는 on-the-fly 로 섞는 게 보통이다.
  • 왜 이벤트 기반인가 업로드 완료를 앱이 알 필요가 없다. 저장소의 ObjectCreated 이벤트가 큐로 가고 워커가 꺼낸다. 앱 서버와 워커가 완전히 분리된다.

코드에서 바뀌는 것앱 코드 변경 없음. 워커는 별도 서비스. MediaStore 가 파생본 URL 규칙만 안다.

Step 12

지리적 확장과 남용 방어

도입 · GeoDNS + 멀티 리전 + API Gateway

넘어가는 신호해외 사용자 피드 지연 300ms 이상, 리전 장애 시 전면 중단. 봇 계정의 게시·팔로우 폭주.

얻는 것

  • 피드 조회가 사용자 근처 리전에서 끝난다. 피드 리스트는 리전 로컬 Redis 에 두고 fan-out 워커가 리전마다 돈다.
  • 게이트웨이에서 토큰 버킷 rate limit, 봇 탐지, 인증을 한곳에 모은다.

대가

  • 게시물은 리전 간 복제 지연 (수백 ms) 뒤에 다른 리전 피드에 나타난다.
  • fan-out 이 리전 수만큼 중복된다. 리전 2개면 Redis 쓰기 2배.

왜 이 기술인가

  • 피드 리스트를 리전 로컬로 두는 이유 피드는 재구성 가능한 파생 데이터다. 리전 간 복제할 가치가 없고, 게시물 이벤트만 미러링하면 각 리전 워커가 자기 Redis 에 다시 만든다. 원천 데이터 (posts, follows) 만 복제한다.
  • GeoDNS vs Anycast URL 단축기와 같다. DNS 라우팅으로 시작, failover 속도가 문제되면 Anycast.
  • API Gateway 를 여기서 넣는 이유 봇의 팔로우·게시 폭주는 fan-out 비용을 직접 올린다. 가짜 계정 1개가 10만 명을 팔로우하면 그 10만 명의 글이 전부 그 계정 피드로 fan-out 된다. 게이트웨이 rate limit 과 계정 단위 한도를 fan-out 앞에 둔다.
  • 대안 · 단일 리전 + 글로벌 CDN 이미지는 CDN 이 이미 가깝다. 피드 API 지연 300ms 가 허용되면 멀티 리전은 미룬다. 리전 장애 허용 여부가 결정한다.

코드에서 바뀌는 것코드 변경 없음. 리전별 Kafka 미러링과 워커 배치.

한눈에 보기

Step도입 기술넘어가는 신호선택 이유코드에서 바뀌는 것
0Spring Boot + PostgreSQL · pull 모델시작점.관계형 모델, pull 이 최소GetHomeFeed 가 FeedSource 포트를 호출하고, 구현은 PullFeedSource (조인 쿼리). FanoutPublisher 는 아직 Noop.
1객체 저장소 (S3) + CDN + presigned URL업로드 트래픽이 앱 서버 대역폭과 디스크를 잡아먹고, 이미지 응답이 피드 API 의 지연을 끌어올릴 때.바이트는 앱을 거치지 않게MediaStore 포트의 구현 S3MediaStore (presign 발급). PublishPost 는 URL 만 받는다.
2로드밸런서 + 앱 수평 확장앱 CPU 70% 이상, 배포 다운타임.무상태 + L7코드 변경 없음. Actuator 헬스체크와 graceful shutdown 설정만.
3PostgreSQL 읽기 복제본Primary CPU 가 피드 조인 쿼리로 포화.결과 캐시보다 쿼리 QPS라우팅 DataSource. @Transactional(readOnly = true) 면 Replica.
4Redis 피드 리스트 · fan-out on write팔로우 300명 이상 사용자의 피드 p99 가 500ms 를 넘고, Replica 를 늘려도 안 내려올 때.비싼 일을 100배 적은 쪽으로FeedSource 구현을 RedisFeedSource 로. FanoutPublisher 구현 SyncRedisFanout. pull 구현은 폴백으로 남긴다.
5Redis 게시물·사용자 캐시 (MGET hydrate)피드 ID 는 Redis 에서 받는데 본문 20개를 채우느라 DB 조회가 요청당 20번.왕복 20번을 1번으로PostCache 구현 RedisPostCache. GetHomeFeed 의 hydrate 단계가 PostCache.getAll(ids) 를 거친다.
6Kafka + fan-out 워커게시 API p99 가 팔로워 수에 비례해 수백 ms 를 넘고, 팔로워 1만 명 계정의 게시가 수 초 걸릴 때.지연을 팔로워 수에서 분리FanoutPublisher 구현을 KafkaFanoutPublisher 로. 워커는 같은 코드베이스의 별도 프로필.
7하이브리드 (셀럽은 pull)팔로워 100만 계정 하나가 글을 쓰면 fan-out 쓰기 100만 건, 워커가 수 분 밀리고 Redis 쓰기가 폭주할 때.상위 0.1% 만 예외 처리GetHomeFeed 가 FeedSource 두 개 (RedisFeedSource, CelebrityPullSource) 를 머지. PublishPost 가 팔로워 수로 fan-out 여부를 결정.
8DB 샤딩 (posts · follows)posts 수십억 행, follows 수백억 행.접근 패턴마다 샤드 키PostRepository, FollowRepository 구현을 샤드 라우팅 버전으로. 포트 시그니처는 그대로.
9랭킹 (피처 저장소 + 배치)제품 지표.식 하나로 시작, 모델은 나중RankingPolicy 포트 추가. 구현 ChronologicalRanking → WeightedRanking.
10Redis 카운터 + 이벤트 원장좋아요 쓰기가 게시 쓰기의 50배.표시용과 원장을 분리CounterStore 포트 추가. LikePost 가 INCR + 이벤트 발행.
11미디어 처리 워커 (libvips)모바일에서 원본 3MB 이미지를 그대로 내려받아 피드 스크롤이 느리고 데이터가 샐 때.CPU 작업은 앱 밖으로앱 코드 변경 없음. 워커는 별도 서비스. MediaStore 가 파생본 URL 규칙만 안다.
12GeoDNS + 멀티 리전 + API Gateway해외 사용자 피드 지연 300ms 이상, 리전 장애 시 전면 중단.파생 데이터는 복제 안 함코드 변경 없음. 리전별 Kafka 미러링과 워커 배치.
